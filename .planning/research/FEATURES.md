## Missouri-Specific Compliance Forms

### Confidence Note

Missouri real estate forms are primarily governed by the Missouri Association of Realtors (MAR) and locally by STL Realtors (St. Louis Association of Realtors, which uses the MARIS MLS system). The forms below represent standard practice as of training knowledge through August 2025. **Before creating BoldSign templates, verify current form versions against STL Realtors / Missouri REALTORS form library at stlrealtors.com or morealtor.com.** Form names and requirements can change between contract cycles.

Confidence: MEDIUM — these are the well-established standard forms; minor naming and version variations expected.

### Single Family Home (SFH) — Seller Forms

| Form | Why Required | Notes |
|------|--------------|-------|
| Residential Sale Contract (Purchase Agreement) | Primary contract for MO residential transactions | Core document; MAR form; all transactions |
| Seller's Disclosure Statement | MO § 339.730 requires disclosure of known material defects | Mandatory by statute for SFH |
| Agency Disclosure (Consent to Dual Agency or Designated Agency) | MO § 339.710 requires agency relationship disclosure before showing | Required at or before first showing |
| Lead-Based Paint Disclosure | Federal law (42 U.S.C. § 4852d) for homes built before 1978 | Required only for pre-1978 homes |
| HOA/Condo Disclosure Addendum | If property is in an HOA | Required when HOA exists |
| Earnest Money Receipt / Trust Confirmation | Documents receipt of earnest money | Typically handled at time of contract execution |
| Addendum to Purchase Agreement (general) | Modifies contract terms | Used as needed for repairs, contingencies |
| Home Inspection Contingency Addendum | Formalizes inspection rights and resolution process | Common, though sometimes in main contract |
| Financing Contingency Addendum | Protects buyer if financing falls through | Common addendum |
| Sale of Buyer's Property Contingency | If buyer must sell existing home first | Used situationally |

### Single Family Home (SFH) — Buyer Forms

| Form | Why Required | Notes |

| Lead-Based Paint Disclosure (Buyer copy) | Federal law; buyer signs acknowledgment | Pre-1978 homes |
| Property Inspection Notice / BINSR equivalent | Buyer's formal response to inspection | Varies by transaction |
| Financing Contingency Removal (or waiver) | Documents buyer waiving financing contingency | Used when applicable |

### Standard MO Closing Checklist Items

These represent the typical milestone progression of a Missouri residential transaction. Confidence: MEDIUM — standard industry practice; specifics may vary by brokerage.

**Contract Phase**
- [ ] Agency disclosure signed and dated
- [ ] Buyer agency agreement executed (post-Aug 2024 NAR requirement)
- [ ] Purchase agreement fully executed (all parties signed)
- [ ] Earnest money deposited with escrow/title company
- [ ] Lead-based paint disclosure completed (pre-1978 homes)
- [ ] Seller's disclosure statement delivered to buyer
- [ ] Transaction timeline confirmed (inspection, financing, closing dates)

**Due Diligence / Contingency Phase**
- [ ] Home inspection completed
- [ ] Inspection response/BINSR sent and resolved
- [ ] HOA documents/resale certificate received and reviewed (condo)
- [ ] Tenant leases reviewed (multi-family)
- [ ] Survey ordered and reviewed (land/lot)
- [ ] Title search ordered

**Financing Phase**
- [ ] Buyer's loan application submitted
- [ ] Appraisal ordered and completed
- [ ] Financing contingency removed or waived
- [ ] Clear to close received from lender

**Pre-Closing Phase**
- [ ] Final walkthrough completed
- [ ] Closing disclosure reviewed (buyer)
- [ ] Settlement statement reviewed (seller)
- [ ] Utility transfer notifications sent

**Closing / Post-Closing Phase**
- [ ] Documents signed at closing
- [ ] Deed recorded
- [ ] Commission disbursement authorization
- [ ] Transaction file archived
- [ ] Client thank-you / referral follow-up

### ShowingTime iCal Feed Data

ShowingTime provides a personal webcal feed accessible at a unique URL per agent. Confidence: MEDIUM — based on training data; verify current field names against ShowingTime's feed output by subscribing to a test feed.

**Standard iCal Fields Present in ShowingTime Feeds**

| iCal Field | ShowingTime Content | Notes |
|------------|---------------------|-------|
| `SUMMARY` | Property address or "Showing at [address]" | Primary display text |
| `DTSTART` | Appointment start time (UTC) | Parsed to local time in calendar |
| `DTEND` | Appointment end time (UTC) | Typically DTSTART + 30 or 60 min |
| `LOCATION` | Property address (full or partial) | Not always present; may duplicate SUMMARY |
| `DESCRIPTION` | Additional notes, agent instructions, access codes | Free-text field; may include lockbox code, notes |
| `STATUS` | CONFIRMED, TENTATIVE, CANCELLED | Important for filtering active showings |
| `UID` | Unique identifier for the showing | Used for deduplication on re-sync |
| `SEQUENCE` | Revision number (increments on updates) | Useful for detecting changes |
| `LAST-MODIFIED` | Timestamp of last change | Useful for change detection |
| `ORGANIZER` | ShowingTime system organizer | Usually a ShowingTime system address |

**What the Feed Does NOT Typically Contain**
- Client/buyer identity (privacy reasons)
- Internal ShowingTime notes private to agent
- MLS number (address is the primary key)
- Showing feedback ratings

**Practical iCal Parsing Notes for GreenDoor**
- Feed URL format: `webcal://showingtime.com/...` or `https://showingtime.com/...` (webcal converts to https for fetch)
- Feed must be fetched server-side (Cloud Function) to avoid CORS
- Re-sync every 30 minutes via scheduled Cloud Function is appropriate
- `UID` field is the deduplication key — do not create duplicate showings on re-sync
- Parse `STATUS: CANCELLED` to mark or remove cancelled showings
- `DTSTART`/`DTEND` may be in UTC or floating time — handle both
- Address matching to existing GreenDoor listings/clients is fuzzy (normalize before comparing)

## Feature Landscape

### Table Stakes (Users Expect These)

Features an agent expects from a compliance-aware CRM. Missing these = product feels incomplete.

| Feature | Why Expected | Complexity | Notes |
|---------|--------------|------------|-------|
| Transaction type on client record | Every transaction has a type (SFH/Condo/MF/Land + Buyer/Seller); agents think in these terms | LOW | Dropdown field on client record; 8 combinations (4 types × 2 sides) |
| Compliance document library organized by transaction type | Agents need quick access to the right forms for each deal type | MEDIUM | Template lookup by transaction type → list of required docs; stored as Firestore config with BoldSign template IDs |
| Send compliance docs for signature directly from client record | Agents expect to initiate e-signature without leaving the CRM | MEDIUM | Extends existing BoldSign integration; adds template selection by transaction type |
| Track which compliance docs have been sent/signed per client | Agents must know their compliance status at a glance | LOW | Status badges (not sent / sent / signed) per document in client record |
| Signed docs auto-saved to client file storage | Agents expect signed PDFs to be in the file system automatically | MEDIUM | BoldSign webhook → Cloud Function → Firebase Storage write to "Closing Documents" folder |
| Client file folder organization | Flat file list becomes unmanageable with 10+ documents | MEDIUM | Create/rename/delete folders; move files between folders; one level of nesting |
| Auto-created "Closing Documents" folder per client | Industry expectation; every deal has a closing docs folder | LOW | Create at client creation or transaction type assignment |
| Closing checklist per client | Agents track milestone progress on every deal | MEDIUM | Seeded by transaction type; checklist items can be checked off; AI can suggest/generate |
| ShowingTime showings visible in GreenDoor calendar | Agents use ShowingTime but want one calendar view | MEDIUM | iCal feed parse → import showings; read-only; synced on schedule |
| Merge fields pre-filled in compliance docs | Agents do not want to type client name/address into every form | HIGH | Map client + listing + agent Firestore fields to BoldSign template merge fields |
| BoldSign sender shows agent's name and email | Agents expect outgoing signature requests to come from them, not a vendor | LOW | BoldSign API parameter: configure sender email/name per request |

### Differentiators (Competitive Advantage)

Features that set GreenDoor apart from generic CRMs or basic document management tools.

| Feature | Value Proposition | Complexity | Notes |
|---------|-------------------|------------|-------|
| AI-powered closing checklist generation | Agent gets a tailored checklist seeded by transaction type and current deal state, not a generic template | HIGH | `askAssistant` Cloud Function extended with transaction context; checklist stored in Firestore |
| Auto-complete checklist items on doc signature | When a compliance doc is signed, the corresponding checklist item ticks automatically | MEDIUM | BoldSign webhook maps document type to checklist item; reduces manual tracking overhead |
| AI check-in for transaction guidance | AI assistant provides contextual guidance based on current checklist state, outstanding docs, and client data | HIGH | Extends existing chatbot; context includes client record, checklist state, signed doc list |
| ShowingTime + GreenDoor calendar unified | No other solo-agent CRM specifically bridges ShowingTime and internal showings in one calendar view | MEDIUM | Showing source badge distinguishes "GreenDoor" vs "ShowingTime" entries |
| Compliance doc status at client-record level | Unlike generic CRMs, compliance doc status (not just files) is a first-class concept tied to transaction type | MEDIUM | Not just a file list — specific named documents with statuses |
| Transaction-type-aware compliance workflow | Automatically shows only the relevant forms for the specific deal type (no manual filtering) | MEDIUM | 8 transaction type combinations; config-driven doc pack per type |

### Anti-Features (Commonly Requested, Often Problematic)

| Feature | Why Requested | Why Problematic | Alternative |
|---------|---------------|-----------------|-------------|
| Build BoldSign template editor in GreenDoor | Agents want to edit document templates in CRM | Massive scope; BoldSign already has a capable template editor; duplicating it creates maintenance burden and reliability risk | Use BoldSign's native template editor; GreenDoor stores only the template ID |
| Multi-state compliance form packs from day one | Expansion opportunity | Each state has unique forms; Missouri is not validated yet; building all states before proving the workflow wastes dev resources and creates data complexity | Missouri-first; add states only after the workflow is proven and adopted |
| Real-time two-way ShowingTime sync | Agents want to create showings in GreenDoor that appear in ShowingTime | ShowingTime has no public write API; attempting to reverse-engineer or scrape would violate ToS and break on any update | Read-only iCal import; ShowingTime remains the source of truth for its showings |
| Persistent AI chat history for closing check-ins | Agents want to "pick up where they left off" with AI | Persistent history increases OpenAI API costs significantly; session-only is sufficient for transactional guidance; history can be reconstructed from checklist state | Use checklist state + client record as context on each session; session-only history |
| Nested folder hierarchy for client files | Agents familiar with Windows/Mac folder trees ask for this | Solo agents with 10–20 files per client do not need deep nesting; nested folders add UI complexity and data model complexity with minimal gain | Single-level folders (flat with one level of naming) is sufficient; implement this constraint intentionally |
| Automated compliance doc reminder emails to clients | Agents want auto-follow-up when docs aren't signed | This requires knowing when a signature is "overdue" (varies by transaction); automated emails without agent oversight create liability risk; agents need to control communication timing | Surface outstanding signature status in the UI; let agent manually send reminders via existing email system |
| MLS data auto-populated into compliance merge fields | Agent wants listing data to auto-pull from MLS | No MLS API integration in scope; manual listing entry is the current pattern; auto-pull would require MLS membership agreements per board | Use manual listing data stored in GreenDoor listings as merge field source |

## Feature Dependencies

```
Transaction Type on Client Record
    └──required by──> Compliance Document Library (type-specific doc packs)
                          └──required by──> Send Compliance Docs for Signature
                                               └──required by──> Track Doc Status per Client
                                                                    └──required by──> Auto-Complete Checklist on Signature

File Folder Management (create/rename/delete/move)
    └──required by──> Auto-Created "Closing Documents" Folder
                          └──required by──> BoldSign Webhook → Auto-Save Signed PDFs

BoldSign Webhook → Auto-Save Signed PDFs
    └──enhances──> Auto-Complete Checklist on Signature

ShowingTime iCal Feed Sync (Cloud Function, scheduled)
    └──required by──> ShowingTime Showings in GreenDoor Calendar

Merge Field Autofill from Client + Listing + Agent Data
    └──required by──> Send Compliance Docs for Signature (useful but separate from basic sending)

AI Closing Checklist Generation
    └──required by──> AI Check-In for Transaction Guidance (check-in needs a checklist to reference)
    └──enhanced by──> Auto-Complete Checklist on Signature
```

### Dependency Notes

- **Transaction Type requires before all compliance features:** Every compliance, checklist, and doc-send feature branches on transaction type. This is the foundational data field — it must exist before any other compliance feature is built.
- **Folder management requires before webhook auto-save:** The "Closing Documents" folder must exist as a concept (and be auto-created) before the webhook can target it as a save destination.
- **BoldSign webhook is a separate integration layer:** It requires a publicly accessible Cloud Function endpoint registered in BoldSign's webhook settings; this is a one-time setup but cannot be unit-tested locally.
- **Merge field autofill is independent of basic sending:** The compliance doc can be sent without pre-filled merge fields (agent fills them manually in BoldSign's UI); autofill is a quality-of-life enhancement, not a blocker for the send feature.
- **ShowingTime sync is fully independent:** It has no dependencies on the compliance or checklist features; it can be built in any sprint order.

## Implementation Notes for Missouri Forms

### BoldSign Template Strategy

BoldSign templates are created manually in the BoldSign dashboard. GreenDoor stores template IDs in Firestore config. The config structure should be:

```
complianceConfig/{state}/transactionTypes/{type}/documents
  - documentId: string (GreenDoor internal key)
  - documentName: string (human-readable)
  - boldSignTemplateId: string (from BoldSign dashboard)
  - required: boolean
  - applicableWhen: string | null (e.g., "pre1978" for lead paint)
  - signers: ["buyer" | "seller" | "agent" | "both"]
  - mergeFields: [{firestoreField, boldSignFieldName}]
```

### Merge Field Sources

| Merge Field Category | Source | Firestore Path |
|---------------------|--------|---------------|
| Agent name | User profile | `users/{uid}.fullName` |
| Agent email | User profile | `users/{uid}.email` |
| Agent license # | User profile | `users/{uid}.licenseNumber` (add field) |
| Brokerage name | User profile | `users/{uid}.brokerage` (add field) |
| Client full name | Client record | `clients/{clientId}.fullName` |
| Client email | Client record | `clients/{clientId}.email` |
| Client phone | Client record | `clients/{clientId}.phone` |
| Property address | Listing record | `listings/{listingId}.address` |
| Property price | Listing record | `listings/{listingId}.listingPrice` |
| Property type | Client record | `clients/{clientId}.transactionType` |
| Closing date | Client record | `clients/{clientId}.closingDate` (add field) |

### ShowingTime iCal Parsing Implementation Notes

- Fetch via Cloud Function (HTTPS GET to webcal URL converted to https)
- Parse using a lightweight iCal parser (ical.js is standard; ~40KB minified)
- Store each showing in Firestore `showings` collection with `source: "showingtime"` field
- Display with read-only badge in calendar; no edit capability on ShowingTime showings
- Deduplication key: `uid` from iCal event + `realtorId`
- Handle `STATUS: CANCELLED` by marking existing Firestore showing as cancelled (not deleted)
- Scheduled Cloud Function: Firebase Scheduled Functions (cron) at 30-minute interval
